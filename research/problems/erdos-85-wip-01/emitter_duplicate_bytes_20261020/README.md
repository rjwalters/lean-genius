# The "duplicated trailing bytes" note in `Erdos85OneHighV2CnfEmit.lean`

The docstring of `emitDimacsWithUnits` in `proofs/Proofs/Erdos85OneHighV2CnfEmit.lean` says that
building and printing the whole formula as one `String` "has produced duplicated trailing bytes in
the native executable". That explanation is wrong. The module is left unchanged so that the
published 893-module closure keeps its byte-identical `.olean` files; this note corrects it.

## What happened (2026-08-14, Lean v4.31.0, macOS arm64)

- It was observed once, for table `03aeeb9e3b51772a`. The output file was 12,504,659 bytes against
  the correct 12,504,319: 340 extra bytes, exactly the last 340 bytes of the correct output repeated.
  The repeat starts mid-line, which is why it showed up as 16 duplicated clauses. `v2cnf check`
  rejected the file (clause-count mismatch).
- Cause: two processes wrote the same shell-redirected file, `/private/tmp/03ae-base.cnf`. An earlier,
  abandoned `lake env lean --run Proofs/Erdos85OneHighV2CnfEmit.lean … > file` run held 340 bytes of
  elaboration warnings in its buffered stdout (`lean --run` prints warnings to stdout). The compiled
  emitter then truncated the file and wrote the correct N bytes, and the orphan finished in the same
  window and wrote 340 + N bytes from offset 0. Only the orphan wrote past byte N, so the file ended
  with the correct output followed by its own last 340 bytes.
- The record of the investigation is the operator's agent session of 2026-08-14. The docstring came
  in with commit `440f9b35196`.

## Evidence

`run.sh` builds a small, Mathlib-free reproducer (`Main.lean`, Lean v4.31.0):

- Single-process emission is byte-exact, whether the whole string is printed at once or in
  4096-clause chunks: 13.0 MB, 21 MB and 50.9 MB, to a file and to a pipe, five repeats each.
- Racing two writers to one redirected file gives exactly the August signature: 340 extra bytes, an
  exact prefix, and an extra tail equal to the reference's last 340 bytes.
- In the v4.31.0 runtime, `lean_io_prim_handle_put_str` is a single `fwrite` with a length check, and
  `lean_string_append`'s in-place update is correct. No upstream Lean issue reports duplicated
  `IO.print` output.

The chunked emitter's first run simply happened when no other writer was active; the chunking
changed nothing.

## Why it does not touch soundness

Every CNF used in a certificate was regenerated by the hash-pinned `v2cnf` executable in a pinned
container and required to hash to the recorded `cnf_sha256` before solving
(`h1_cert_full_20261001/cert_row.py`, `h1_bank_check_20261006/bank_check_row.py`). A malformed file
is rejected, not certified.
