## §2 — Cluster-level root-cause analyses

### Cluster A (errors #1–#4): `cast_PathMN_val` simp dead

**Symptom.** At `1911:96` Lean emits the `unsolved goals`
```
⊢ ↑(cast ⋯ ⟨List.take … ++ List.drop …, ⋯⟩) =
  List.take … ++ List.drop …
```
plus an explicit `linter.unusedSimpArgs` warning that both
`cast_PathMN_val` and `Subtype.coe_mk` are unused inside the
`simp only [gvCanonInv, dite_true, tailSwapPath, cast_PathMN_val,
Subtype.coe_mk]` at line `1912:50`. The simp recipe does normalize
`gvCanonInv` and `dite_true` and `tailSwapPath`, but the residual
`↑(cast (congrArg (PathMN _) _) _)` pattern is not rewritten.

The local lemma at `1849`
```
private lemma cast_PathMN_val {m n₁ n₂ : ℕ} (h : n₁ = n₂) (e : PathMN m n₁) :
    (cast (congrArg (PathMN m) h) e).val = e.val := by
  cases h; rfl
```
is itself well-typed and proof-correct (`cases h; rfl` works), but
its pattern `(cast (congrArg (PathMN m) h) e).val` no longer fires
under Lean 4 v4.26.0 simp matching on `↑(cast _ _)`.

**Hypothesis.** Lean 4 v4.26.0 changed `↑` (Subtype coercion via
`Subtype.val`) elaboration so that `↑(cast … ⟨val, prop⟩)` no longer
β-reduces to `(cast … ⟨val, prop⟩).val` before simp's pattern matcher
fires.

**Mechanic kit (Cluster A).**
* Re-state `cast_PathMN_val` as `@[simp]` with the LHS pattern
  rewritten to use `↑` explicitly:
  ```
  @[simp] private lemma cast_PathMN_coe {m n₁ n₂ : ℕ} (h : n₁ = n₂) (e : PathMN m n₁) :
      (↑(cast (congrArg (PathMN m) h) e) : List _) = ↑e := by
    cases h; rfl
  ```
* OR replace each `simp only [..., cast_PathMN_val, ...]` with an
  explicit `unfold gvCanonInv` + `rw [cast_PathMN_val (by …) _]`
  giving the equality explicitly.
* Verify with `lake build Proofs.BallotProblemOQ03OQ02`.

### Cluster D (errors #10–#15): `canonCross_eq` PART 1 rewrite-pattern failures

**Symptom.** Multiple `rw [colEntry_eq_ci]` / `[colEntry_eq_cj]`
tactic invocations fail to find the pattern `↑(t'.snd ci)` (resp.
`↑(t'.snd cj)`) in the goal. The goal still has the form
```
⊢ N / (r * r) % yBound cfg ≤
    cfg.sources ⟨N / r % r, hiv⟩ + colEntry (↑(t'.snd ⟨N / r % r, hiv⟩)) (…)
```
where `t'.snd` is applied to the encoded Fin index, not `ci` (a
let-bound projection).

**Hypothesis.** Lean v4.26.0 changed the order of `let`-zeta in goals,
so `ci` (defined as `let ci := canonI cfg hwf t ht`) is no longer
visible to the `rw` matcher when the goal has been simped to use the
underlying `⟨N / r % r, hiv⟩` form.

**Mechanic kit (Cluster D).**
* Replace `rw [colEntry_eq_ci]` with
  `rw [show (t'.snd ⟨N / r % r, hiv⟩ : _).val = (t.snd …).val from colEntry_eq_ci _ rfl]`
* OR introduce `set ci := canonI cfg hwf t ht with hci_def` before
  the rewrite, then `simp only [← hci_def]` to surface `ci`.
* OR use `conv_lhs => rw [show t'.snd … = … from …]`.

### Cluster E (errors #16–#21): `gvCanonInv_involution_inverse` `hN` substitution

**Symptom.** A hypothesis `hN : canonCrossN cfg hwf (gvCanonInv cfg hwf t hht) hht'
= canonCrossN cfg hwf t hht` is supposed to substitute under
`t' := gvCanonInv cfg hwf t hht`, but Lean reports type mismatches
at `2326`/`2328`/`2332` where `hN` has type
`canonCrossN … t' hht' = canonCrossN … t hht` but is expected to
have type `canonCrossN … t' hht' / r % r = canonCrossN … t hht / r % r`
(division-and-mod-mismatched).

The proof presumably uses `hN ▸ rfl` or `rw [hN]` to close
arithmetic facts about `canonCrossN`, but the substitution doesn't
fire because the `let t' := gvCanonInv …` is not zeta-reducing into
`canonCrossN cfg hwf t' hht'`.

Plus `2330:35: No goals to be solved` — the previous line over-closed.

**Mechanic kit (Cluster E).**
* Replace `rw [hN]` with `simp only [hN]` (which normalizes
  positional rewrites) OR with explicit
  `simp only [hN, Nat.div_mod_equiv]` at each of `2326`/`2328`/`2332`.
* Remove the line at `2330` whose goal is already closed.
* For `2336`/`2338` unsolved goals `c₀ + (y₀ - cfg.sources ci) = ki`,
  need `splitPosAt`-unfold. Add `simp only [splitPosAt] at *; omega`
  or `rfl` if `splitPosAt` was changed to definitional.

### Cluster F (errors #22–#23): `nth_rw 2` targets wrong occurrence

**Symptom.** At `2370`/`2386` the proof is:
```
have hkj_drop : ((t.2 cj).val.take kj).drop kj = [] := by
  nth_rw 2 [← List.length_take_of_le hkj_le]; exact List.drop_length
```
The intent: rewrite the SECOND `kj` (the `.drop kj`) into
`(L.take kj).length`, then `List.drop_length : L.drop L.length = []`
closes. But `List.drop_length` reports a type mismatch — the rewrite
hit the wrong `kj` occurrence.

**Hypothesis.** Lean v4.26.0 changed the textual numbering of
sub-term occurrences for `nth_rw`. The second `kj` in
`((t.2 cj).val.take kj).drop kj` is no longer at position 2 under
the new traversal order.

**Mechanic kit (Cluster F).**
* Try `nth_rw 1 [← List.length_take_of_le hkj_le]` first.
* If that fails, replace with `conv_lhs => rw [show kj = ((t.2 cj).val.take kj).length from (List.length_take_of_le hkj_le).symm]`.
* OR replace the whole tactic with the equivalent:
  ```
  have : ((t.2 cj).val.take kj).length = kj := List.length_take_of_le hkj_le
  rw [← this, List.drop_length]
  ```
