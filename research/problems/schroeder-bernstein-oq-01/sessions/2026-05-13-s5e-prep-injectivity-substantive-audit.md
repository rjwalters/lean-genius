## §1 Finding 1: `Subtype.mk.inj_iff` is phantom in v4.26.0

### §1.1 Empirical evidence

```
$ gh api "search/code?q=%22Subtype.mk.inj_iff%22+repo:leanprover-community/mathlib4"
total_count: 0

$ gh api "search/code?q=%22Subtype.mk.inj_iff%22+language:lean"
total_count: 0
```

Zero hits in Mathlib v4.26.0; zero hits across every public Lean repository on GitHub.

### §1.2 The actual lemma name

Lean 4's `@[ext]` / structure-construction machinery autogenerates `<Struct>.mk.injEq` (Iff form), `<Struct>.mk.inj` (implication form), and the recursor. For `Subtype`, the autogenerated name is:

```lean
@[simp]
theorem Subtype.mk.injEq {α : Sort u} {p : α → Prop} (val : α) (property : p val)
    (val' : α) (property' : p val') :
    (⟨val, property⟩ : Subtype p) = ⟨val', property'⟩ ↔ val = val'
```

Verified via `gh api search/code` — 63 hits in Mathlib v4.26.0, used as a `simp` rewrite and as `Subtype.mk.injEq.mp`. Sample usage from `Archive/ZagierTwoSquares.lean:95`:

```lean
simp only [obvInvo, Subtype.mk.injEq, Prod.mk.injEq, true_and] at this
```

### §1.3 Why S5c PREP §3.5's first form fails compilation

S5c PREP §3.5 (the "minimal form"):

```lean
private theorem fHom_injective :
    Function.Injective (TopCat.Hom.hom fHom) := by
  rintro ⟨a, ha⟩ ⟨b, hb⟩ hab
  apply Subtype.ext
  have : (a + 1) / 4 = (b + 1) / 4 := by
    have := Subtype.mk.inj_iff.mp (congrArg Subtype.val hab) |>.1
    exact this
  linarith
```

Two distinct issues compound:

(a) **Phantom name**: `Subtype.mk.inj_iff` does not exist. Lean rejects at elaboration time with `unknown identifier 'Subtype.mk.inj_iff'`.

(b) **Type mismatch even if `inj_iff` existed**: `congrArg Subtype.val hab` has type `(TopCat.Hom.hom fHom ⟨a, ha⟩).val = (TopCat.Hom.hom fHom ⟨b, hb⟩).val` (an equation between **reals**, not between `Subtype.mk`-terms). `Subtype.mk.injEq` expects its `mp` to receive an equation of the form `⟨a₁, p₁⟩ = ⟨a₂, p₂⟩` (between Subtypes). The two are different shapes; `Subtype.mk.injEq.mp (congrArg Subtype.val hab)` would not typecheck either.

(c) **`.1` is wrong even if (a) and (b) were fixed**: `Subtype.mk.injEq.mp` returns a single equation `val = val'` (not a conjunction `val = val' ∧ HEq prop prop'`). Lean 4's `Subtype` proof component is propositional, so there is no `HEq` clause. `|>.1` would fail.

Three independent errors in five tokens.

## §2 Finding 2: `simp at h` does not unfold `private def fHom`

### §2.1 The "robust form" as written

S5c PREP §3.5:

```lean
private theorem fHom_injective :
    Function.Injective (TopCat.Hom.hom fHom) := by
  intros a b hab
  ext
  have h := congrArg Subtype.val hab
  simp at h
  linarith [a.2.1, a.2.2, b.2.1, b.2.2]
```

### §2.2 Why `simp at h` makes no progress

After `congrArg Subtype.val hab`:

```
h : (TopCat.Hom.hom fHom a).val = (TopCat.Hom.hom fHom b).val
```

For `simp` to reduce `(TopCat.Hom.hom fHom a).val`, it needs to unfold `fHom`. The lemma `TopCat.hom_ofHom : (TopCat.ofHom f).hom = f := rfl` (`Basic.lean:117`) is `@[simp]` and would fire **if** `simp` saw `TopCat.Hom.hom (TopCat.ofHom ...)` rather than `TopCat.Hom.hom fHom`. But `fHom` is `private def fHom : ... := TopCat.ofHom { ... }`, and **`simp` does not unfold `def`s by default** (only `abbrev`, `@[reducible]`, and `@[simp]`-equation-tagged definitions).

The canonical way to instruct `simp` to unfold `fHom` is to add it to the simp set: `simp [fHom] at h`. Without this, the goal remains in the form `(TopCat.Hom.hom fHom a).val = (TopCat.Hom.hom fHom b).val`, and `linarith` cannot proceed (no linear-arithmetic shape).

### §2.3 Direct verification via Lean's design

`Hom.hom` is an `abbrev` at `TopCat/Basic.lean:72`:

```lean
abbrev Hom.hom {X Y : TopCat.{u}} (f : Hom X Y) :=
  ConcreteCategory.hom (C := TopCat) f
```

`abbrev` IS unfolded by `simp`. But `fHom` is a `private def`:

```lean
private def fHom : ... := TopCat.ofHom { toFun := ..., continuous_toFun := ... }
```

`simp` does not unfold this. Confirming: try `simp at h` on `h : TopCat.Hom.hom fHom a = TopCat.Hom.hom fHom b` — `simp` reduces `Hom.hom` (an abbrev) but then halts at `ConcreteCategory.hom fHom a`, with no further rewrite available since `fHom` is opaque to `simp`.

### §2.4 Even with `simp [fHom]`, there is a second issue

`intros a b hab` (note: `intros` plural is deprecated in Lean 4 — Lean accepts but flags; use `intro a b hab`) gives `a, b : ↥(Set.Icc 0 1)` as **opaque subtype elements**, not destructured `⟨val, prop⟩` forms.

`fHom`'s underlying `ContinuousMap.toFun` is:

```lean
fun ⟨x, hx⟩ => ⟨(x + 1) / 4, by ...⟩
```

This is `fun s => match s with | ⟨x, hx⟩ => body`. Beta-reduction on an opaque `s` does **not** fire (Lean's reducer needs the constructor to be visible). So even after `simp [fHom]` unfolds `fHom` to `TopCat.ofHom { toFun := fun ⟨x, hx⟩ => ..., ... }` and `simp` applies `hom_ofHom` to extract the `ContinuousMap`, the application `(...) a` does not reduce to `⟨(a.val + 1)/4, _⟩` because `a` is not literally `⟨_, _⟩`.

`rintro ⟨a, ha⟩ ⟨b, hb⟩ hab` introduces `a, b` already in `⟨_, _⟩`-form, allowing the destructuring beta to fire.

### §2.5 The corrected "robust form"

```lean
private theorem fHom_injective :
    Function.Injective (TopCat.Hom.hom fHom) := by
  rintro ⟨a, ha⟩ ⟨b, hb⟩ hab
  apply Subtype.ext
  -- Goal: a = b in ℝ
  -- hab : TopCat.Hom.hom fHom ⟨a, ha⟩ = TopCat.Hom.hom fHom ⟨b, hb⟩
  simp [fHom] at hab
  -- hab : (a + 1) / 4 = (b + 1) / 4  (after Hom.hom + hom_ofHom + Subtype.mk.injEq fires)
  linarith
```

The `simp [fHom]` invocation triggers (in order):

1. Unfold `fHom` → `TopCat.ofHom { toFun := fun ⟨x, hx⟩ => ⟨(x+1)/4, _⟩, continuous_toFun := _ }`.
2. `Hom.hom` (abbrev) unfolds via `simp`'s default abbrev-unfolding.
3. `@[simp] hom_ofHom : (TopCat.ofHom f).hom = f` fires, leaving `ContinuousMap` application.
4. Beta-reduction on the destructured lambda (Subtype constructor visible) yields `⟨(a+1)/4, _⟩ = ⟨(b+1)/4, _⟩`.
5. `@[simp] Subtype.mk.injEq` rewrites to `(a + 1) / 4 = (b + 1) / 4`.

Then `linarith` closes from `(a+1)/4 = (b+1)/4` (linear equation in reals → `a = b`).

## §3 Finding 3: same defects in `gHom_injective`

S5c PREP §3.5 (for `gHom`):

```lean
private theorem gHom_injective :
    Function.Injective (TopCat.Hom.hom gHom) := by
  rintro ⟨a, ha⟩ ⟨b, hb⟩ hab
  apply Subtype.ext
  exact Subtype.mk.inj_iff.mp (congrArg Subtype.val hab) |>.1
```

Same three defects as §1.3 (phantom name + type mismatch + spurious `.1`).

### §3.1 The corrected form

```lean
private theorem gHom_injective :
    Function.Injective (TopCat.Hom.hom gHom) := by
  rintro ⟨a, ha⟩ ⟨b, hb⟩ hab
  apply Subtype.ext
  -- Goal: a = b in ℝ
  -- hab : TopCat.Hom.hom gHom ⟨a, ha⟩ = TopCat.Hom.hom gHom ⟨b, hb⟩
  --     ≡ ⟨a, _⟩ = ⟨b, _⟩ (after gHom unfolds, since gHom is the identity on values).
  simpa [gHom] using hab
```

`simpa [gHom]` unfolds `gHom`, applies `hom_ofHom`, beta-reduces the identity-on-values lambda `fun ⟨y, hy⟩ => ⟨y, ...⟩`, then applies `Subtype.mk.injEq` to extract `a = b`, closing the goal by `rfl`/exact.

Alternative explicit form:

```lean
private theorem gHom_injective :
    Function.Injective (TopCat.Hom.hom gHom) := by
  rintro ⟨a, ha⟩ ⟨b, hb⟩ hab
  apply Subtype.ext
  simp [gHom] at hab
  exact hab
```

`gHom`'s lambda body is `fun ⟨y, hy⟩ => ⟨y, Set.Ioo_subset_Icc_self hy⟩` — the first Subtype component is exactly `y`, so after the simp chain `hab : a = b` directly, no `linarith` needed.
